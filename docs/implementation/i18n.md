# Internationalization

The web UI is translated. English (`src/web/i18n/en/`) is the source catalog. French, Italian, and European Portuguese (`pt-PT`) translate every English key in every namespace; German and Spanish keep the grandfathered core coverage and fall back to English per key elsewhere. Every user-facing string in `src/web` comes from a message catalog, and numbers, dates, lists, sizes, and costs are formatted for the active locale.

## Pieces

No dependency: lookup is about 150 lines on top of `Intl`. The English catalog is part of the startup bundle; a translation chunk loads only when it is needed.

## Using it

```ts
import { t } from "@/i18n";
import { formatDate, formatLanguageName } from "@/i18n/format";
import { Trans } from "@/i18n/react";

t("common.cancel");
t("shell.tabTitle", { title });                     // placeholder required
t("sidebar.selectedCount", { count });              // plural entry, `count` required
formatDate(item.createdAt);                         // "Oct 30, 2026" in English, "30. Okt. 2026" in German
formatLanguageName("es");                           // "Spanish" / "Spanisch" / "español"
formatNativeLanguageName("pt-PT");                  // "Português (Portugal)" in every UI language
<Trans k="schedules.lastRunError" params={{ date, error: <span className="text-error">{message}</span> }} />
```

Keys are `namespace.key`, typed from the English catalog: a wrong key, a missing placeholder, or a plural entry without `count` fails `npm run typecheck`.

### Catalog rules

- One namespace per area (`thread`, `sidebar`, `memory`, ...). `common` holds words used in many areas (Cancel, Save, Delete). Area text stays in its area even when the English word repeats, because other languages may need a different word in a different context.
- Entries are a string, or plural forms `{ one: "{count} chat", other: "{count} chats" }` (`other` is required; translations use their own `Intl.PluralRules` categories).
- Keys are camelCase words without dots.
- Lookup tables of keys are typed `PlainMessageKey` (keys without params), e.g. `as const satisfies Record<Kind, PlainMessageKey>`, so `t(TABLE[kind])` compiles.
- Write whole sentences with placeholders. Never build a sentence by concatenating translated pieces or by adding `"s"` for plurals: word order and agreement differ between languages.
- Use keys literally (`t("memory.title")`). No computed keys. Two tests enforce both directions: a catalog key that appears nowhere literally fails, and a literal `t()` key that is missing from `en` fails. The scan ignores `command:`/`reason:`/`fallback:` values (command ids) and requires a non-identifier character before `t(` so `commandTarget(` is not mistaken for `t(`.
- Never call `t()` at module top level. Modules evaluate before `loadLocale` resolves. Store the `MessageKey` in constants (`labelKey: "keyboard.newChat"`) and call `t()` when rendering.
- Numbers, dates, sizes, costs, and lists go through `format.ts`. Direct `toLocaleString`, `toLocaleDateString`, `toLocaleTimeString`, `toLocaleUpperCase`, `toLocaleLowerCase`, `new Intl.`, and `localeCompare` are rejected in `src/web` outside `i18n/`, `vendor/`, `theme/`, and `components/settings/theme/`. Case-folding for search uses plain `toLowerCase()`, and id ordering uses a plain comparator so it does not change with the UI language.

### What is not translated

- Text sent to models (tool descriptions, system prompts in `src/server/prompts.ts`), stored data (chat titles, memory content, message translations), and log output.
- Proper names: product and provider names, theme names, font families, model ids, language names in code blocks.
- Server error messages. Known failures carry a stable code and are shown from `src/web/i18n/en/errors.ts`; a safe specific server detail (for a field or a quota number) stays English because `src/server` has no catalog. See `docs/implementation/errors.md`.

## Locale selection

`main.tsx` calls `loadLocale(localeLoaders)` before the first render. It picks the stored choice (`localStorage["okaychat:locale"]`), then `navigator.languages`, matched by exact tag (case-insensitive) and then by language subtag in registry order, falling back to `en`. It loads only that translation chunk and sets `<html lang>` and `dir`; English needs no chunk. A chunk that fails to load leaves English text with English `lang`/`dir`.

Only one Portuguese catalog ships, `pt-PT`. Generic `pt`, `pt-BR`, and any other Portuguese region resolve to it through the language-subtag rule; a stored `pt-BR` is shown in European Portuguese but is never rewritten to `pt-PT`. Likewise `fr-CA` → `fr`, `it-CH` → `it`. A resolved browser language is never stored as an account choice.

The locale is fixed for the page's lifetime. `setLocale(tag | null)` stores the choice and reloads.

The account's language wins on every device, but the page has already rendered by the time settings arrive:

- `PATCH /settings { locale }` stores `user_settings.locale` canonicalized (`FR-fr` → `fr-FR`, `pt-pt` → `pt-PT`). Any structurally valid BCP 47 tag within 35 characters is accepted, shipped or not (`pt-BR`, `nl`); malformed tags are a 400, `null` follows the browser, omission leaves the value alone. `translationTarget` follows the same rules. Validity is structural: ICU canonicalizes well-formed tags even for languages it has no data for. `GET /settings` returns valid stored strings in canonical form without rewriting the row, and drops malformed or non-string values so the browser language applies.
- `saveLocalePreference(tag)` writes the server first, then `setLocale(tag)`, so a failed save never changes this device.
- `applyAccountLocale(userId, account)` runs in `state/data.ts` `load()` after settings arrive. When the account value differs from `localStorage`, it mirrors the value and reloads **once**, guarded by `sessionStorage["okaychat:locale-sync"] = "<userId>:<account|browser>"`. If session storage is blocked the marker cannot survive a reload, so it does not reload at all rather than loop. `i18n/index.ts` must not import `@/lib/api` (`api.ts` imports `t`), which is why this lives in `account-locale.ts`.

The General settings page has a Language row (`setting-language`) listing "Use browser language" first, then `shippedLocales()` labeled with their autonyms (`formatNativeLanguageName`: the registry's reviewed `nativeName`, else `Intl.DisplayNames` in the tag's own language, else the tag) and sorted with `compareText` in the current UI language. A saved tag this build does not ship stays visible as an extra option. The message-translation and voice pickers keep `formatLanguageName` (names in the UI language).

## Coverage contract

Coverage policy is test data in `testing/catalog-rules.ts`, selected by each registry row's `coverage`:

- **source** (`en`): the catalog itself; nothing to translate.
- **legacy** (`de`, `es` only, grandfathered; the registry test rejects any other legacy row): CORE plus the activity and keyboard keys they already translated. These two remain partial and fall back to English per key.
- **wave** (`fr`, `it`, `pt-PT`, and every future row): **every key in every English namespace**, including namespaces added in later features. `requiredKeys("wave")` is derived from the English source, so a new English key is immediately required in each wave locale. At this baseline that is 4,684 keys across 56 namespaces per locale.

Plural entries supply every category of the language (`Intl.PluralRules(tag).resolvedOptions().pluralCategories`; `one`, `many`, `other` for all three), and `many` may repeat `other`. Every supplied entry, required or optional, is validated the same way: known namespace and key, the same string or plural shape as English, non-blank text, `other` plus only the language's own categories, no unknown placeholder, and every non-`count` placeholder present in each form, with `{count}` required in a French singular because French selects the singular for zero as well. Legacy rows keep the CORE + supplement requirement.

A separate gate, `testing/translation-quality.ts`, rejects sentence-like English left unchanged (whitespace-insensitive) in a wave catalog after placeholders, separators and all-caps technical tokens are stripped. Every translated plural form is checked, and a form English lacks (`many`) is compared with English `other`. French strings must use a no-break space before `? ! ; : % »` and after `«` (tested). The reviewed allowlist holds API parameter literals (`provider/model`), protocol names (`Streamable HTTP`), product and command names, URL placeholders and units that are the same word in the target language. Single-word cognates are out of scope for the machine gate and belong to human review.

Lookup: a missing namespace or key uses the whole English entry with English plural rules; plural forms are never merged across languages. A translated plural picks the active language's category, then its own `other`. Numeric placeholders are formatted for the active locale even inside English fallback text.

The unused-key scan reads only runtime web code: `i18n/en`, `i18n/locales`, `i18n/testing`, `fixtures` directories, and tests never count as usage. The missing-key scan covers literal `t("…")`, `<Trans k="…">`, `…Key: "…"` properties, and typed `PlainMessageKey` tables, including `format.ts` and `react.tsx`.

## RTL readiness

`textDirection` and `applyLocale` set `<html dir>`; no RTL language ships, so production stays `ltr`.

All six shipped languages are left to right; `textDirection` is script-aware where the runtime exposes text info (`az-Arab` → rtl), with a language list fallback.

New UI files use logical properties (`ms-*`, `me-*`, `ps-*`, `pe-*`, `start-*`, `end-*`, `text-start`, `text-end`) and join `RTL_CHECKED_FILES` in `rtl.test.ts`, which rejects physical direction utilities. Older UI files still contain many physical-direction utilities (`text-left`, `text-right`, `left-*`, …). Shipping an RTL language needs those converted, bidirectional content isolation, and a full layout pass; logical properties and `dir` alone do not certify RTL support.

## Adding a language

1. Add one row to `src/shared/ui-locales.ts` with the canonical tag, the reviewed autonym, its direction, and `coverage: "wave"`.
2. Add `src/web/i18n/locales/<tag>.ts`, named exactly by that tag: `import type { Translation } from "../index";`, then `const xx: Translation = { … }; export default xx;` in English namespace and key order. Explicit text only: no spreads, imports of other catalogs, generated entries, or `t()` calls.
3. Translate every wave key and supply each plural category the language has.
4. Run `npm test`. Loading, matching, the picker, and the coverage gates pick the language up with no other change; the registry test fails if the file and row disagree.

Translations are reviewed by a fluent speaker before shipping; tests check shape, not language quality. Keep identifiers, codes, header names, placeholders, and model-facing text untouched.

## Team channels

`channels.*` is one English namespace covering the workspace, fields, settings, messages, AI states, transport, errors, and notices. Dates use `formatDate`/`formatTime`, counts use the plural entries, and reason/error mappings use `web/lib/channel-error.ts`. Web-only text is translated; model prompts and server error sentences stay English. See `docs/implementation/channels.md`.

## Message translation

Translating a chat message is a separate feature with its own storage, prompt, and quota rules; it is not part of the UI locale system. See `docs/implementation/message-translation.md`.
